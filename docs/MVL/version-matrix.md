## Retail vs Steam (0.98c/d/e)

Same size, identical import tables, identical notable strings. Only diffs:
- PDB path: `C:\GamesX\GTA Vice City\mvl\vehmod_retail.pdb` vs
  `...\vehmod_steam.pdb` (all of 0.98c/d/e).
- One dump filename: `mvl/dump640FE5h.txt` (retail) vs `mvl/dump63FF95h.txt`
  (steam) at 0.98e only — implies a single hardcoded game-exe address
  (0x640FE5 retail vs 0x63FF95 steam) baked into a debug dump path; the
  retail/steam patch-site divergence is minimal but real.
- Conclusion: steam variant = same code with a small set of exe addresses
  retargeted for the steam exe. Diffing retail↔steam code is a cheap way to
  find exe-address-dependent patch sites.

## Rejected hypotheses

- "0.96d's +117KB jump is a new feature subsystem" — rejected: the jump is
  dominated by the static-CRT toolchain switch (MSVCR100 import table
  removal + KERNEL32 heap/W-API batch + RTTI strings); feature content of
  0.96d per changelog is small (COLL/COL2, ALT+4 XML-gen).
- "python33.dll is imported by 0.98" — rejected: no python33 import table
  entry in any version; Py* names are GetProcAddress strings (dynamic load).
- "vehmod_chooser.flt is an older vehmod.flt" — rejected: 532 bytes, 1 import;
  it is a stub, not a functional loader.
- "0.98c's +149KB is the WAV/save feature" — partially rejected: a large
  share is the VS2013-era CRT/toolchain bump (W-API batch, threadpool APIs,
  manifest); WAV loader + save XML + opcodes are the feature remainder.
